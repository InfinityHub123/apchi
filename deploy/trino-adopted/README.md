# A Trino nobody configured with Apchi in mind

The fixture Adoption needs, and the only one that can prove anything about it.

Every other tier 2 test runs against `deploy/trino-dev/`, whose access-control and
user-mapping files are **generated by Apchi** and drift-checked in CI. A discovery that
round-trips a file Apchi wrote proves the generator is deterministic. It does not prove Apchi
can read somebody else's Trino, which is the entire question §15 asks.

So everything here is hand-written, deliberately, and **nothing here is generated or
drift-checked**. If a generator changes, this directory must not follow: the point is that it
was written by someone who had never heard of Apchi.

## What it is configured like

Everything is in a place Apchi would not have chosen, because that is what an un-adopted
Cluster looks like:

| | Here | Where Apchi writes |
|---|---|---|
| access-control rules | `/etc/trino/theirs/rules.json` | `/etc/trino/access-control/rules.json` |
| user mapping | `/etc/trino/theirs/user-mapping.json` | `/etc/trino/user-mapping/user-mapping.json` |
| resource groups | `/etc/trino/theirs/groups.json` | `/etc/trino/resource-groups.json` |
| catalogs | a ConfigMap at `/etc/trino/catalog` | an emptyDir seeded from a Secret |

Each is named by Trino's own configuration -- `security.config-file`,
`user-mapping.file`, `resource-groups.config-file`, `catalog.config-dir` -- which is how
discovery finds them, and the reason it follows Trino's configuration rather than assuming
Apchi's layout.

There is no catalog-seed initContainer and the catalog directory is a read-only ConfigMap.
Both are §16 violations on purpose: they are what the cutover has to fix, and the catalog one
is the reason the cutover must come *after* the seed.

## What is in the files that Apchi cannot hold

**An `impersonation` block.** Apchi's grant model has no vocabulary for it, so it exercises
#89's preserve path for real rather than against a constructed string.

**A `tables` rule matching a set of catalogs with one regex.** One identity's access to a
set, where Apchi's model has a name -- preserved rather than approximated.

**Two user-mapping patterns**, where Apchi holds one. The second becomes an Admin value
(§13.3).

## What no manifest can express

A catalog created by `CREATE CATALOG` after the pod started. It lives only in the
coordinator's writable store, so Apchi can name it and cannot reconstruct it -- the test
creates it itself, and supplying its properties is the step that makes the discovery
adoptable.

## Names

Everything is prefixed `adopted-` so it cannot collide with `deploy/trino-dev/`, which shares
the namespace and whose baseline fixture would otherwise report this deployment as drift.

## The cutover manifest is in a subdirectory

`cutover/trino.yaml` is the same Trino *after* step 4 -- the deployment change an Admin makes
once Apchi has seeded. It is not in this directory because `kubectl apply -f
deploy/trino-adopted/` has to bring up the Cluster as it was **before** Apchi; applying the
cutover with it points the coordinator at Secrets that do not exist yet, and Trino refuses to
boot with `file does not exist: /etc/trino/user-mapping/user-mapping.json`.

Read it as a diff against `00-config.yaml` and `10-trino.yaml`: that diff is the whole answer
to "what do I have to change".

Part of that answer is `securityContext.fsGroup` and a `defaultMode` on the two volumes that
carry credentials. Those are not violations before the cutover -- this Cluster mounts nothing
but ConfigMaps until then, and §16's eighth precondition only looks at Secrets that hold
something worth restricting.
